# flotilla — agent notes

macOS-only Tauri v2 app (Rust + a static web frontend in `src/`) in the same family as curator, warden and lector. Windows, each a workspace where any tab can head a group of documents (usually a Google Drive folder); documents opened from it list beneath it, each is open once across every window, and the session restores on relaunch.

Deferred work, and what unblocks each item: `docs/FOLLOWUPS.md`.

## Layout

- `crates/flotilla-core` — platform-neutral, Tauri-free core: `identity` (document keys and kinds), `model` (windows of groups built from the config's mirror types, one-copy registry across windows, Recent, each window's Incoming queue of handed links, which `Workspace::receive` places or queues and whose item ids hash the link like tab ids do, so a link is queued once across windows; a `TabId` is the FNV-1a of its `DocKey`, so it is stable across reloads), `nav` (what each navigation does), `session` (the session file: each window's active tab and Incoming queue, Recent, and the loaded tabs; `windows_manifest`, the `windows.json` link routers read).
- `src-tauri` — the Tauri shell: `state` (`AppState` and its lock rule), `windows` (the `WindowHost` shell-core's managed `WindowSet` builds windows through: one OS window per config `[[window]]`, matched to its workspace window by title; its label only names the OS window and its webviews, and a rename is carried into the workspace by the new title, never the reported label), `tabs` (content webviews labelled `child_label(<hosting window label>, <TabId>)` and parsed back only via `tabs::tab_of`; the `intercept` hook; `sync`, per open window, with `created`/`hole` keyed by window label), `sidebar` (the chrome DTO, with the window's Incoming rows as chrome-core's `incoming`; a row's `icon` is its kind's glyph in `src/icons/`), `detach` (popped-out tabs: one shell-core detached window per `detached` tab, labelled from the tab id so geometry persists; the tab stays in its workspace window, so it docks back into whichever window holds that title, reopened if closed), `commands` (each chrome acts on its own window's workspace window; `open_handed` takes a link another app hands over, bare or as `flotilla://open?window=…&group=…&url=…` (`RunEvent::Opened`, the scheme registered in `Info.plist`), into the named window, else the last focused, else the first, held in `EARLY_LINKS` until setup has built the state; `incoming_action` runs an Incoming row's buttons), `menu` (the menu bar, acting on the focused window, with the Window menu from `WindowSet::entries`; the Group menu and the row context menu share `menu_state_for`, which takes the tab's current page for Set Home's reasons; Set Home re-keys the tab in place, written as one `url` edit via `write::through_rekey`; a DTO push rebuilds the menu bar only when its `MenuKey` changed), `persist` (debounced save to `session.json` in the app data dir, then `windows.json` beside it from the same snapshot), `migrate` (at launch, before the config is read, a version 1 session's groups move into the config and the session is rewritten as v2), `write` (write-through: `write::through` runs a model op, diffs the workspace before/after into config-core edits and applies them, all under `write::Gate`, which each config reload also takes and re-reads the file under, so a reload or format-on-save never lands mid-commit; a failed write undoes the change, shows a notice and reloads the file. The gate is not reentrant and never covers view work, since a webview create/close can run `intercept` synchronously. `run_on_main_thread` called on the main thread runs inline, so view work that must wait for the stack to unwind (after a reload, or `intercept`'s Open) goes through `crate::defer`, which posts from another thread), `config` (settings plus `[[window]]`s on config-core's `Window<DocTab, WindowExtras, FlotillaGroup>`; `parse` adds open-once across windows by `identity::identity`; `src/default-config.toml` is its starter, include_str!'d, holding the `flotilla` window and a commented example of every window key, and `parses_every_documented_key` keeps the two in step). Plus `build.rs`, `tauri.conf.json`, `Info.plist` (merged into the bundle's), `capabilities/`.
- Every workspace change ends in `tabs::changed`: the pure `tabs::plan` decides which webviews to close, create (the active tab's, plus, hidden, the tabs the session saved as loaded, `AppState::warm`; no other), show and hide; then the pure `detach::plan` decides which popped-out windows to open and close (every `detached` tab has one, so relaunch reopens them), the DTO is pushed and a save scheduled. Every change that touches groups, documents, names, `collapsed` or `detached` goes through `write::through` first; the file's reload then rebases the workspace on the new windows (`Workspace::rebase`), keeping each window's active tab where it survives, so the echo of the app's own write changes nothing. The model appends new groups at the end of their window because the config does. A name or title is written once: new groups and documents are written named by their URL, and the page's title replaces that only while it is still the URL (`tabs::adopt_title`). The model never makes a detached tab a window's `active`: activating one leaves `active` alone and records a raise, which `commands::mutate` (via `detach::apply`) turns into raising its window.
- `src/` — the chrome page; `chrome.js` binds chrome-core's `ChromeSidebar` to the Rust commands. `src/inject/` holds the page scripts every content webview runs (`tabs::create`'s `extra_init`), each gating itself to the site it serves. `chrome-core.{css,js}` are generated by `build.rs`, git-ignored.
- `scripts/tooling.env` — per-app parameters for shell-core's release scripts, which `build.rs` materializes (git-ignored).

## Shared cores

What lives where: shell-core owns everything a window or webview needs (geometry, menu spine, the web layer, `detach`, `watch`, release scripts); chrome-core owns the sidebar view and self-update; config-core owns file primitives (path, starter seeding, formatter, the shared `Window` and its structural edits). flotilla owns only what is its own: documents and groups (`flotilla-core`) and the wiring that binds them to those cores. shell-core's `WindowSet` owns window lifecycle (New Window…, the banner's Edit/Delete Window…, the Window menu, quitting on the last close, the home surface when no window is open); flotilla's `FlotillaHost::write` applies its config edits under `write::Gate`, released before the set's `rename`/`delete` re-enter the host.

chrome-core, shell-core and config-core are pinned by `rev` in `src-tauri/Cargo.toml`; shell-core also in `crates/flotilla-core/Cargo.toml`, all its dep lines at one rev (`scripts/tooling.env`'s CORES lists both manifests, so `shell-pin` rewrites both). Local-dev loop: `just chrome-dev` / `shell-dev` / `config-dev`, re-pin with `chrome-pin` / `shell-pin` / `config-pin`; the `[patch]` lines in the root `Cargo.toml` stay commented in git (`just gate` and `.githooks/pre-commit` refuse otherwise). The toolchain is pinned in `rust-toolchain.toml`, in lockstep with the sibling apps.

## Commands

`just run`, `just test`, `just gate` (the check; there is no CI), `just build`, `just install`, `just icon` (regenerates `src-tauri/icons` from `icon.svg` through plate), `just release`.

## Releases

Version source of truth is `src-tauri/Cargo.toml`; tag `v<version>`, GitHub release with notes. The updater private key lives at `~/.tauri/flotilla-updater.key` (never committed); its public half is `plugins.updater.pubkey` in `tauri.conf.json`. `createUpdaterArtifacts` is enabled only by shell-core's `scripts/release.sh`, never in the committed config, so keyless from-source builds work.

Branch model: main-only until 0.1.0, when it becomes `main` + `dev` with work landing on `dev`. `just release` runs from a primary checkout on a clean `dev` equal to `origin/dev` (shell-core's `release.sh` refuses otherwise), with the Apple signing/notary env and the updater key; it gates, builds and notarizes a universal binary, tags `v<version>`, fast-forwards `main` and publishes the GitHub release. Bump `version` in `src-tauri/Cargo.toml` first (`flotilla-core` is `publish = false` and its version is not the app's); curate the README against what the app now is. `DRY_RUN=1 just release` prints the side effects instead.
